# ERP Provisioning

## Concept

mux can fetch its configuration from a central ERP system. This enables:
- **Central management**: IT admins configure database connections and VPN tunnels in the ERP, and all mux instances pick up the config automatically
- **Secret distribution**: The ERP provides database passwords and WireGuard keys -- users don't need to know them
- **Hybrid operation**: ERP-managed connections coexist with locally-configured ones

## Current Implementation Status

The ERP provisioning feature is **implemented but based on assumptions** about what the ERP API will look like. The actual ERP endpoint does not exist yet and needs to be built or adapted.

---

## Assumptions (Need Review)

### 1. API Method and Authentication

**Assumption**: The ERP provides an HTTP endpoint that accepts GET requests with a Bearer token.

```
GET https://erp.example.com/api/mux/config
Authorization: Bearer {token}
Accept: application/json
```

**Open questions**:
- Does this endpoint exist or does it need to be built?
- Is Bearer token the right auth method? Would API keys, OAuth, or session cookies be better?
- Is GET the right method? Some APIs use POST for config retrieval.
- Should there be versioning (`/api/v1/mux/config`)?

### 2. Response Format

**Assumption**: The ERP returns a JSON object with two arrays: tunnels and connections.

```json
{
  "tunnels": [
    {
      "name": "office-vpn",
      "privateKey": "base64-encoded-32-byte-private-key",
      "peerPublicKey": "base64-encoded-32-byte-public-key",
      "peerEndpoint": "vpn.example.com:51820",
      "allowedIPs": "10.100.0.0/16",
      "tunnelAddress": "10.100.0.42/32",
      "dns": "10.100.0.1",
      "presharedKey": "base64-optional",
      "mtu": 1420,
      "keepalive": 25
    }
  ],
  "connections": [
    {
      "name": "production",
      "type": "postgresql",
      "host": "10.100.0.5",
      "port": 5432,
      "user": "readonly_user",
      "password": "secret-from-erp",
      "database": "production",
      "readOnly": true,
      "tunnel": "office-vpn",
      "instructions": "Production PostgreSQL. Read-only access to customer data."
    },
    {
      "name": "analytics",
      "type": "clickhouse",
      "host": "10.100.0.10",
      "port": 9000,
      "user": "analyst",
      "password": "secret-from-erp",
      "database": "analytics",
      "tunnel": "office-vpn",
      "instructions": "ClickHouse analytics database."
    }
  ]
}
```

**Open questions**:
- Should the ERP provide WireGuard private keys directly? This means the ERP knows all VPN keys.
- Could keys be generated client-side and only the public key sent to the ERP?
- What happens when a user has multiple devices? Same keys everywhere or per-device?
- Should the `instructions` field come from the ERP? This controls what the AI agent "knows" about the connection.

### 3. Token Provisioning

**Assumption**: Each user gets a provisioning token from their ERP "My Account" page. They paste this into mux's web UI.

**Flow**:
1. User logs into ERP web interface
2. Navigates to "My Account" or similar page
3. Copies a provisioning token (generated by ERP)
4. Opens mux web UI -> ERP Provisioning section
5. Pastes endpoint URL and token -> Save
6. Clicks "Sync Now" to fetch config

**Open questions**:
- Does the ERP have a "My Account" page or settings area?
- Can the ERP generate long-lived API tokens for users?
- Should tokens be scoped (e.g., read-only config access)?
- Should tokens expire? If so, how does renewal work?

### 4. Error Handling

**Current behavior**:
- ERP fetch timeout: 15 seconds
- Non-200 HTTP status -> error with status code and response body (first 512 bytes)
- ERP failure at startup -> warning logged, app continues with local config only
- ERP failure during UI sync -> HTTP 502 returned to UI, local config unchanged

**Assumption**: The ERP being temporarily unreachable is normal and should never prevent mux from working.

### 5. Config Merge Behavior

**Current behavior**:
- **Tunnels**: ERP tunnels are checked first. On name collision, ERP wins (local tunnel with same name is hidden).
- **Connections**: Both ERP and local connections are included. No deduplication by name.
- **Source tracking**: All ERP items are marked with `source: "erp"`.
- **UI protection**: ERP-managed items cannot be edited or deleted in the UI.

**Open questions**:
- Should connection names collide? What if ERP and local both define "production"?
- Should the ERP be able to disable/override local connections?
- Should there be a way to "pin" a local connection so ERP can't shadow it?

## Setup via Web UI

The web UI always shows the ERP Provisioning section:

1. **Endpoint**: Text field for the ERP API URL
2. **Token**: Password field for the bearer token (shows "SAVED" when stored in keychain)
3. **Save**: Persists endpoint to TOML, token to keychain
4. **Sync Now**: Fetches from ERP, merges with local config, re-registers connections

## Setup via Environment Variables

```bash
MUX_ERP_ENDPOINT=https://erp.example.com/api/mux/config
MUX_ERP_TOKEN=your-provisioning-token
```

These override TOML config and keychain values.

## What Happens at Startup

```
1. Config loaded (TOML + keychain + env)
2. If ERP endpoint AND token are both set:
   a. HTTP GET to endpoint (20s timeout)
   b. If error -> log warning, continue without ERP data
   c. If success -> parse JSON, mark items as source="erp"
   d. Call cfg.SetERP() to store in runtime (not persisted to TOML)
3. Continue with WireGuard tunnel setup, tool registration, etc.
```

ERP data is fetched fresh on every mux startup. It is not cached between restarts.

## What Happens During Sync (UI)

```
1. User clicks "Sync Now" in web UI
2. POST /api/erp/sync (no request body)
3. Server calls erp.Fetch() with stored endpoint + token
4. If error -> HTTP 502 with error message
5. If success:
   a. cfg.SetERP() replaces previous ERP data
   b. New ERP connections are registered as MCP tools
   c. Response: {"status": "synced", "tunnels": N, "connections": N}
6. UI refreshes to show updated connections
```

Note: Sync during runtime does not re-establish WireGuard tunnels. Tunnel changes require mux restart.
